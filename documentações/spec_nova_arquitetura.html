Especificação da Nova Arquitetura

Versão 2.0 28/07/2026 Gmail API + IA Classificadora

§1 O que é este documento

Este documento é a especificação da nova arquitetura do Oráculo 360 — a que substituirá os 16 scripts do pipeline atual por um sistema mais direto: leitura do Gmail via API + IA classificadora.

Ele é a fonte da verdade do novo projeto. Toda regra, decisão, campo, categoria e exemplo documentado aqui foi validado com Michel ou anotado como pendente de validação.

⚠️ Campos 6, 7 e 8 (em §10) estão marcados como PENDENTE — aguardam simulações de threads reais antes de serem definidos.

§2 Funcionalidades do sistema

O sistema tem três peças:

#PeçaO que faz
F1Leitor do GmailLê a caixa oraculo@finaud.com.br via Gmail API. Coleta threads novas e atualiza as existentes.
F2Classificador IAPara cada thread, identifica a categoria regulatória, o cliente, o lado responsável (Finaud ou cliente) e o prazo.
F3Painel operacionalExibe threads ativas organizadas por prazo, com destaque visual de urgência. Permite filtrar por responsável e categoria.

§7 Dado sensível e segurança

Os e-mails contêm dados regulatórios de instituições financeiras — posições, saldos, relatórios de risco. Regras:

  • Nada vai para nuvem de terceiros (exceto o texto enviado à API Claude para classificação — sem dados numéricos brutos)
  • Credenciais Gmail ficam no .env local — nunca no git
  • Backups seguem o padrão data/json/pipeline/backups/AAAAMMDD_HHMM_motivo/

§10 Campos que cada e-mail precisa ter

Para classificar e rastrear corretamente, o sistema precisa extrair estes campos de cada mensagem:

Campo 1 — De (remetente real)
O endereço de quem enviou o e-mail. A Gmail API devolve o endereço real (ex.: noe.santana@amarilfranklin.com.br). Se for @finaud.com.br = colaborador Finaud. Qualquer outro = cliente ou externo.
Campo 2 — Para (destinatário)
Para quem o e-mail foi enviado. Em geral suporte@finaud.com.br ou o e-mail pessoal de um colaborador Finaud.
Campo 3 — CC (cópias)
Lista de endereços copiados. Usado para identificar outros participantes da thread. O oraculo@finaud.com.br aparece aqui quando a conversa foi copiada para captura.
Campo 4 — Reply-To
Para onde as respostas devem ir — campo presente na Gmail API, ausente no MCP. Importante para identificar caixas compartilhadas como remetente real.
Campo 5 — Assunto
O título do e-mail. Principal sinal de categoria para a IA. Padrões: código CADOC direto (DDR 2011, DRM (2060)), nome do documento (Balancete de Câmbio), tipo de situação (REJEITADO, INDÍCIO DE PROBLEMA).
Campo 6 — Corpo ⚠️ PENDENTE
O texto da mensagem que a IA vai ler. Aguarda definição: como pré-processar, o que a IA recebe de cada tipo, como tratar histórico acumulado e mensagens curtas demais.
Bloqueado por: simulações de threads reais (RETORNO_BACEN, DLO/DLI, SUPORTE)
Campo 7 — Anexos ⚠️ PENDENTE
Lista de arquivos em anexo. Aguarda definição: tipos relevantes por categoria, padrões de nome, o que a IA extrai de cada um.
Campo 8 — Thread ID e Data ⚠️ PENDENTE
ID único da thread (para rastrear toda a conversa) e data de cada mensagem. Aguarda definição: como a IA usa o thread_id; como extrair a data de referência do CADOC.

§11 Regras de classificação

11.1 — Prioridade dos sinais

A IA usa os sinais em ordem de confiança: (1) Código CADOC no assunto; (2) Padrão de nome de anexo; (3) Conteúdo do corpo; (4) Histórico da thread. Sinais de alta confiança (ex.: ZIP CNPJ_2011_DATA.zip) sobrepõem sinais ambíguos.

11.2 — Identificar o lado responsável

SituaçãoLado responsável
Finaud entregou remessa — aguarda cliente transmitirCliente
Cliente enviou dados — aguarda Finaud processarFinaud
Finaud orientou — aguarda confirmação do clienteCliente
BACEN comunicou — aguarda ação de qualquer parteDepende de quem respondeu por último

§12 Modelo de rastreamento (duas camadas)

Um e-mail pode tratar de mais de um CADOC ao mesmo tempo. O sistema registra cada entrega separadamente:

CamadaO que rastreiaExemplo
Camada 1 — E-mailA comunicação: quem enviou, quando, o que disseThread "Segue DDR, DRM e DLI — Mirae março/2026"
Camada 2 — EntregasUma linha por CADOC mencionado, com prazo próprioDDR_2011 + DRM_2060 + DLI_2062, cada um com seu prazo e status
Por que duas camadas? Sem isso, um e-mail com DDR + DRM + DLI geraria apenas uma entrada no painel. Os prazos são diferentes — misturar resulta em entregas perdidas.

§14 Catálogo de categorias — o que a IA precisa saber

Resumo dos sinais de detecção por categoria. O spec completo (com fluxo passo a passo, o que não é, e exemplos de assuntos reais) está em documentações/ESPECIFICACAO_NOVA_ARQUITETURA.md §14.

CategoriaSinais de alta confiançaCuidado — pode confundir
DDR_2011 Assunto com "DDR" ou "2011"; anexo prefixo RD_; ZIP CNPJ_2011_*.zip Não confundir com 4111 (contábil) ou DLO/DLI (mensais)
CADOC_4111 Assunto "4111", "CADOC 4111"; anexo CADOC 4111.xlsx; ZIP CNPJ_4111_*.zip "Conglomerado" no assunto sozinho não identifica — verificar contexto
DRM_2060 Assunto "DRM 2060", "DRM2060_MMAAAA"; anexo Saldos DRM.xlsx "COMUNICACAO DE INCONSISTENCIA no DRM" → é RETORNO_BACEN
DLO_2061 COS4010+COS4016 + planilha LEC juntos; "DLO 2061"; ZIP Cos4010.zip Sem LEC = DLI; "ECSA (S5) - COS4010" = S5 (S5 prevalece)
DLI_2062 "DLI 2062"; COS4010+COS4016 sem LEC; ZIP CNPJ_2062_*.zip "Aviso Bacen - DLI" pode ser RETORNO_BACEN — verificar contexto
DRL_2160 "DRL 2160", "Colchão de Liquidez"; planilha DRL.xlsx; ZIP CNPJ_2160_*.zip DRL + DDR no mesmo e-mail → registrar ambos (modelo 2 camadas)
S5 "S5", "Resultado Quantitativo S5"; COS4010 + contexto S5 "S5 para S4" = SUPORTE (mudança de segmento prudencial)
SUPORTE Por eliminação — nenhum código CADOC + dúvida/acesso/reunião/boleto "- Situação -" + nome CADOC = SUPORTE (não entrega)
RETORNO_BACEN "REJEITADO", "INDÍCIO DE PROBLEMA", código VCRD* ou DLO000* no corpo Urgente — D+3 para responder ao BACEN
FORCAPITAL "FORCAPITAL", "ForCapital", "projeção de capital"; destinatário suporteforcapital@ "projeção" de Basileia ou prazo = DLO/DLI, não ForCapital
